> 上層文件：`00_overall_spec.md`
> 範圍一前篇：`07-1_logging_audit_spec.md`
> 相關：`06-2_deposit_withdraw_spec.md`（鏈上入出金流程）

## 一、需求方規格

範圍二把日誌與帳本從「純內部模擬」延伸到「真實鏈上出入金」的稽核。帳本的三條核心原則不變：只新增不修改、餘額變動與帳本紀錄同時發生、對帳等式恆成立。以下是新增的稽核需求。

### 1. 出入金狀態轉移必須全程留痕

範圍二的出入金不再是一發生就完成，而是會經歷多個階段：

- **入金**：偵測到鏈上轉入後先進入「處理中」，等鏈上確認數達標才「完成」；若交易被丟棄或發生鏈重組則「失敗」。因為入金採「先確認、後入帳」，失敗時尚未動用戶餘額，不需退款。
- **出金**：先扣用戶內部餘額後才對外廣播，廣播並確認後「完成」；若廣播失敗或交易被丟棄則「失敗」。因為出金採「先扣款、後廣播」，失敗時餘額已被扣走，必須退還（見第 3 點）。

每一次狀態轉移都要留下可稽核的紀錄。

### 2. 同一筆鏈上交易不可重複入帳（冪等）

鏈上交易的監聽會因輪詢、服務重啟、任務重試而重複偵測到同一筆交易。系統必須保證同一筆鏈上交易只入帳一次，否則用戶餘額會憑空增加。出金端同理：同一筆出金請求不可重複廣播、重複扣款。

### 3. 出金失敗要以反向紀錄退款

帳本只能新增、不能修改。出金失敗時，不可刪改當初的扣款紀錄，而是新增一筆方向相反、金額相同的紀錄把餘額加回。兩筆紀錄同時保留，完整還原「發生過什麼」；對帳等式在退款後依然成立。同時將該筆出入金標記為失敗。

### 4. 鏈上手續費是獨立的業務事件

交易所代為廣播鏈上交易所付的網路手續費，與交易所自身抽取的交易手續費是完全不同的兩回事：前者付給區塊鏈網路、只在碰鏈時發生，後者是交易所的收入、純內部搬移。兩者的成本歸屬、會計科目與報表口徑都不同，必須各自獨立記錄，絕不可合併。

### 5. 鏈上餘額對帳（償付能力 / 儲備證明雛形）

除了範圍一「單一錢包餘額等於其所有帳本紀錄總和」的內部自洽外，範圍二新增一條更重要的對帳：

> 交易所在鏈上實際持有的資產總量，必須大於或等於所有用戶內部餘額（可用 + 凍結）的總和。

用戶的內部餘額本質上是交易所開出的借據。若鏈上實際持有少於欠用戶的總額，即代表資不抵債（挪用、被駭或帳務錯誤）。此等式即「儲備金證明（Proof of Reserves）」的雛形。系統應定期查詢交易所所有鏈上地址的實際餘額，與用戶內部餘額總和比對，差額超過門檻即告警。

### 6. 稽核鏈路必須可追溯到鏈上憑證

出入金的帳本紀錄要能一路追溯到對應的鏈上交易憑證，再連到區塊瀏覽器，形成完整的稽核鏈路。

## 二、開發方規格

> 對應 app：`ledger`；鏈上入出金流程見 `06-2_deposit_withdraw_spec.md`。

本層承接需求方規格，補充技術約束。帳本紀錄維持 append-only、與餘額變動同一原子交易、對帳不變量恆成立（範圍一鐵則不變，見 `07-1`）。

### 1. 出入金紀錄的狀態機

出入金紀錄本身**不是** append-only，其狀態欄位本來就要隨流程更新（勿與 append-only 的帳本紀錄混淆，後者永不可更新）。狀態轉移：

```
入金:  PENDING ──確認數達標──▶ DONE
                └──交易丟棄 / 鏈重組──▶ FAILED   (未入帳，不退款)

出金:  PENDING ──廣播且確認──▶ DONE
                └──廣播失敗 / 交易丟棄──▶ FAILED   (★必退回餘額)
```

關鍵不對稱：入金「先確認後入帳」，故失敗不退款；出金「先扣款後廣播」，故失敗必退款。

### 2. tx_hash 冪等約束

- **DB 層唯一約束**：對鏈上交易識別碼（tx_hash）加唯一性。注意範圍一遺留的空字串——範圍一的 tx_hash 允許為空字串預設值，直接加 `unique=True` 會被多筆空字串衝突炸掉。兩種處理擇一：
  - 做法 A（推薦）：PostgreSQL 部分唯一索引，只對「非空」的 tx_hash 唯一，舊有空字串照樣共存。
  - 做法 B：改為可為 NULL（PostgreSQL 的 unique 允許多個 NULL），並以資料 migration 把既有空字串轉為 NULL。
  - 多鏈情境：不同鏈的 tx_hash 理論上不相撞，保險可用（鏈, tx_hash）複合唯一。
- **程式邏輯層檢查**：入帳前先查該 tx_hash 是否已有完成紀錄，有則跳過。DB 約束是最後一道保險絲，不是唯一防線（與 `04-1` 三層防護：鎖 / 原子性 / 不變量思路一致）。

### 3. 出金廣播的併發防護

出金廣播前需先鎖住該筆出入金紀錄（`select_for_update`），確認其狀態仍為 PENDING、尚未取得 tx_hash，否則代表已送出過。以太系須留意 nonce 管理：同一熱錢包地址併發簽署易撞號，導致交易卡住或被覆蓋。

### 4. 反向分錄退款

出金失敗時不可刪改原扣款分錄，改為新增一筆方向相反、金額相同的分錄退回餘額，並將該筆出入金狀態更新為 FAILED。範例：

| 時間 | 事件 | 餘額類別 | delta | 說明 |
|---|---|---|---|---|
| T1 | 出金扣款 | 可用 | −5000 | 發起出金，先扣款 |
| T2 | 出金失敗退回（新增） | 可用 | +5000 | 上鏈失敗，反向退回 |

兩筆分錄皆保留，對帳不變量仍成立（−5000 + 5000 = 0）。帳本記錄的是歷史而非現況，現況由 delta 總和推得。

### 5. 新增的分錄事件類型

- **出金上鏈失敗退回**：對應第 4 點的反向分錄。
- **鏈上網路手續費（gas）**：交易所代付、通常轉嫁用戶。此類型與交易手續費必須嚴格分離——交易手續費為交易所內部抽成、與鏈無關；網路手續費付給區塊鏈網路、僅碰鏈時出現。依 `07-1` §3.2 顆粒度原則，兩者屬不同業務事件，各自獨立記錄。

### 6. 鏈上餘額對帳

定期（例如每小時）以 RPC 查詢交易所所有鏈上地址（熱錢包、冷錢包、各充值地址）的實際餘額，與所有用戶內部餘額（可用 + 凍結）總和比對；鏈上持有必須 ≥ 內部負債總和，差額超過門檻即告警。此即償付能力 / 儲備金證明雛形，範圍一無「鏈上實際持有」可比，故為範圍二才成立的稽核。

### 7. ref_type 的延伸與稽核鏈路

出入金分錄的 ref 仍指向出入金紀錄，鏈上憑證（tx_hash）存於該筆出入金紀錄上，稽核鏈路為：帳本紀錄 → 出入金紀錄 → tx_hash → 區塊瀏覽器，全程可追溯。（真正 DEX 化後 ref 才會直接指向鏈上事件，屬另立規格的獨立階段，見 `CLAUDE.md`。）

### 8. 技術約束 / 注意事項

- 失敗的出金一律以反向分錄處理，不可改舊分錄「修正」，否則破壞 append-only、稽核失去意義。
- 冪等不可只靠程式檢查，必須同時有 DB 唯一約束；併發下缺約束仍會重複入帳。
- tx_hash 不可直接加 `unique=True`，須用部分唯一索引或 NULL 化處理範圍一遺留的空字串。
- 網路手續費不可併入交易手續費，否則成本歸屬與報表全錯。
- 入金失敗不可退款：入金採先確認後入帳，失敗時尚未入帳，誤退等於送錢。
