## 0. 這一步在改什麼

`LedgerEntryModel` 的**核心設計完全不變**——append-only、與餘額變動同 atomic、對帳不變量，
這三條鐵則在範圍二依然是鐵則。

變的是三件事：

1. `DepositWithdrawModel` 的 **`status` 狀態機真的動起來**（範圍一直接 `DONE`）。
2. 需要**鏈上冪等性**（`tx_hash` 唯一），防止同一筆鏈上交易被入帳兩次。
3. 出金**會失敗**，失敗要退款——而 append-only 的帳本**不能改舊帳，只能寫反向分錄**。

外加一個新的稽核維度：**內部帳本 vs 鏈上實際餘額的對帳**（§5）。

## 1. `DepositWithdrawModel` 的狀態機

範圍一：建立即 `DONE`，`updated_at` 沒有意義。範圍二狀態真的會轉移：

```
入金：  （偵測到鏈上轉入）PENDING ──確認數達標──▶ DONE
                            └──交易被丟棄/鏈重組──▶ FAILED   （本來就沒入帳，不必退款）

出金：  （已扣內部餘額）  PENDING ──廣播且確認──▶ DONE
                            └──廣播失敗/交易丟棄──▶ FAILED   （★必須退回餘額，見 §3）
```

**關鍵不對稱**：入金是「**先確認、後入帳**」（沒確認就不動餘額，所以失敗不必退款）；
出金是「**先扣款、後廣播**」（不先扣，用戶能重複花同一筆錢），**所以出金失敗一定要退款**。

這也解釋了為什麼 `DepositWithdrawModel` **不是 append-only**——它的 `status` 本來就要更新。
（別跟 `LedgerEntryModel` 搞混，後者永遠不可更新。）

## 2. 鏈上冪等性：`tx_hash` 必須唯一

**同一筆鏈上交易只能入帳一次。** 監聽服務會重複掃到同一筆交易（輪詢、重啟、Celery 重試都會），
不擋的話用戶餘額會憑空多好幾份。

最穩固的防線是讓 `tx_hash` **唯一**——但這裡有個範圍一留下的岔路要處理：

> **問題**：範圍一的 `tx_hash` 是 `blank=True, default=""`，所以資料庫裡會有**一堆空字串**。
> 直接加 `unique=True` 會立刻衝突（多筆 `""` 不唯一）。

兩個解法（升級時擇一）：

- **做法 A（推薦）：PostgreSQL 部分唯一索引** — 只對「非空」的 `tx_hash` 唯一：
  `UniqueConstraint(fields=["tx_hash"], condition=~Q(tx_hash=""), name="uniq_tx_hash_when_present")`。
  舊資料不用動，範圍一的空字串照樣共存。
- **做法 B：改成 `null=True`** — 空值存 `NULL`（PostgreSQL 的 unique 允許多個 `NULL`），
  再直接 `unique=True`。需要一次資料 migration 把 `""` 轉成 `NULL`。

> **多鏈情境**：不同鏈的 `tx_hash` 理論上不會撞，但保險起見可以用 `unique_together = (chain, tx_hash)`。

除了 DB 約束，**程式邏輯也要先檢查**：入帳前先查「這個 `tx_hash` 是否已有 `DONE` 紀錄」，有就跳過。
DB 約束是最後一道保險絲，不是唯一防線——這與 M6 的思路一致
（三層防護：鎖 / 原子性 / 不變量，見 `04-1`）。

**出金的冪等**同理：廣播前 `select_for_update` 鎖住該筆 DW、確認 `status` 仍是 `PENDING` 且 `tx_hash` 為空，
否則代表已經送過了。以太系還要注意 **nonce 管理**（同一熱錢包地址併發簽署容易撞號 → 交易被卡住或覆蓋）。

## 3. 出金失敗 → 寫反向分錄，不改舊帳

出金流程是「先扣內部餘額、再上鏈廣播」。若廣播失敗或交易被丟棄，**必須把餘額退回去**。

但 `LedgerEntryModel` 是 **append-only**——**不可以**把當初那筆 `WITHDRAW` 的分錄刪掉或改掉。
正確做法是**寫一筆新的、方向相反的分錄**把餘額加回來：

| 時間 | reason | balance_field | delta | 說明 |
|---|---|---|---|---|
| T1 | `WITHDRAW` | AVAILABLE | −5000 | 發起出金，先扣款 |
| T2 | `WITHDRAW_FAILED`（新增） | AVAILABLE | **+5000** | 上鏈失敗，退回 |

同時把該筆 `DepositWithdrawModel.status` 改成 `FAILED`（它可以更新）。
兩筆分錄都留著，帳就能完整還原「發生過什麼」——這正是 append-only 的價值：
**帳本記錄的是歷史，不是現況**。現況由 delta 總和推出來（對帳不變量依然成立：−5000 + 5000 = 0）。

> 這與 `07-1` §3 鐵則 1「寫錯就再寫一筆反向修正」是同一個心法，只是這裡不是「寫錯」，
> 而是「業務上真的失敗了」。

## 4. 新增的 `reason`

| reason | 說明 |
|---|---|
| `WITHDRAW_FAILED` | 出金上鏈失敗，退回餘額（§3） |
| `NETWORK_FEE` / `WITHDRAW_FEE` | **鏈上手續費（gas）**，交易所代為廣播所付、通常轉嫁給用戶 |

> **`NETWORK_FEE` 與 `TRADING_FEE` 是完全不同的兩回事，絕不可合併**（見 `07-1` §5.1）：
> `TRADING_FEE` 是**交易所的抽成**，純內部帳本搬移、與鏈無關；
> `NETWORK_FEE` 是**付給區塊鏈網路**的費用，只在碰鏈時出現。
> 兩者的成本歸屬、會計科目、報表口徑都不一樣。
>
> 依 `07-1` §3.2 的顆粒度原則：它們是**不同的業務事件**，所以各自一個 reason。

## 5. 新的稽核維度：鏈上餘額對帳（償付能力）

範圍一的對帳只有一條：**錢包餘額 == 該錢包所有 ledger delta 總和**（內部自洽）。

範圍二多了一條**更重要**的：

> **交易所鏈上實際持有的幣（熱錢包 + 冷錢包 + 各充值地址）
> ≥ 所有用戶內部餘額的總和（available + frozen）。**

因為用戶的餘額只是**借據**——如果交易所鏈上真正持有的幣**少於**它欠用戶的總額，
那就是**資不抵債**（挪用、被駭、或帳算錯）。這條等式就是所謂
**儲備金證明（Proof of Reserves）** 的雛形，也是 FTX 之類的交易所崩潰時失守的那條線。

實作上：定期（例如每小時）用 RPC 查交易所所有地址的鏈上餘額，
與 `SUM(WalletModel.available + frozen)` 比對，差額超過門檻就告警。

> 這是範圍二才可能做的稽核——範圍一根本沒有「鏈上實際持有」這個東西可比。
> 它也很好地說明了為什麼帳本要記得這麼嚴謹：**帳本是你證明自己有償付能力的唯一依據。**

## 6. `ref_type` 的延伸

範圍一的 `ref_type` 指向內部 model（`order` / `transaction` / `deposit_withdraw` / `manual`）。
範圍二時出入金的分錄仍然指向 `DepositWithdrawModel`，**而鏈上的憑證（`tx_hash`）存在那筆 DW 上**，
所以從帳本 → DW → `tx_hash` → 區塊瀏覽器，稽核鏈路是完整的。

（未來真的 DEX 化時，`ref` 才會直接指向鏈上事件——但那是另立規格的獨立階段，見 `CLAUDE.md`。）

## 7. 常見坑

- **改舊分錄來「修正」失敗的出金** → 破壞 append-only，稽核就失去意義。一律寫反向分錄。
- **只靠程式檢查冪等、沒加 DB 唯一約束** → 併發下仍會重複入帳。約束是最後的保險絲。
- **`tx_hash` 直接加 `unique=True`** → 會被範圍一遺留的空字串炸掉。用部分唯一索引（§2 做法 A）。
- **把 `NETWORK_FEE` 併進 `TRADING_FEE`** → 成本歸屬與報表全錯。
- **入金失敗時「退款」** → 入金是先確認後入帳，失敗時**根本還沒入帳**，不需要退。誤退等於送錢。
