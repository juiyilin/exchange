# 細部規格 — 用戶與錢包（member）〔範圍二：測試鏈〕

> 上層文件：`00_overall_spec.md`　範圍一前篇：`02-1_member_wallet_spec.md`
> 相關：`01-2_currency_spec.md`（幣別的鏈上屬性）、`06-2_deposit_withdraw_spec.md`（鏈上入出金流程）

## 一、需求方規格

### 1. 內部帳本維持不變

範圍二不改動內部帳本。內部帳本仍是交易所對用戶的欠款紀錄（記著交易所欠某用戶多少幣），可用餘額與凍結餘額的語意、餘額不變量、鎖策略全部照舊。

真正的鏈上資產不存放於內部帳本，而集中於交易所自有的鏈上錢包（熱錢包／冷錢包）。因此範圍二在用戶與錢包主題要新增的並非「錢包」，而是充值地址管理——一個屬於鏈上世界的新概念。

需要區分三個容易混淆的概念：內部帳本（欠款紀錄）、鏈上錢包（私鑰的集合）、以及用戶的住址（個人資料），三者互不相干。

### 2. 專屬充值地址

#### 2.1 為什麼每個用戶要有專屬地址

鏈上轉帳不會附帶付款人身分資訊。交易所收到一筆入金時，鏈上只會告知「有若干數量的幣進入了某個地址」，並不會說明是誰付的、該記到誰頭上。

因此交易所以地址本身作為身分識別：事先替每個用戶、每個幣別配置一個專屬充值地址，並記住該地址是配給哪一位用戶。監聽服務看到資金進入該地址，即可判定應入帳給對應的用戶。

#### 2.2 配置規則與邊界

- 每位用戶、每個幣別配置一個專屬地址；同一用戶在同一幣別只會有一個地址。
- 任一充值地址在全系統範圍內不得重複配給不同用戶，否則入金會記到錯誤的對象上。
- 部分同格式的鏈系可共用同一地址（同一地址可在這些鏈上收款），但各鏈餘額彼此獨立；不同格式的鏈系則須各自配置。設計時可考慮讓同一用戶在相容鏈系間共用一個地址。

#### 2.3 私鑰保管的安全邊界

若為每個用戶每個幣別各自獨立產生並保管一把私鑰，用戶數量龐大時保管成本無法承受。

需求上採用「由單一主秘密可推導出無限多組地址」的分層確定性作法：只要妥善保住那一組主秘密，任何時候都能重新推導出所有充值地址的控制權，因此系統本身無需逐一保存每個地址的私鑰。

私鑰保管的安全邊界：主秘密不得進入資料庫、不得納入版本控制、不得寫死於程式中，須以受保護的方式（如環境變數或金鑰管理服務）保管。主秘密外洩等同所有用戶的充值地址均被掌控。

### 3. 用戶端可做的動作

- 用戶端唯一新增的入金相關動作，是取得（或首次取得）自己在指定幣別的專屬充值地址。此動作只回傳地址，不變動任何餘額，且用戶只能取得屬於自己的地址。
- 入帳永遠由系統（監聽服務）觸發，不存在「用戶主動請求為自己入金」的動作。用戶端能做的只有兩件事：取得一個地址，然後自行在鏈上轉帳（詳見 `06-1` §2.2）。

### 4. 交易所自有錢包（熱／冷）

此為交易所的資金庫，並非用戶的錢包。

- 熱錢包：私鑰連網、可自動簽名，用於出金；僅存放少部分資金以降低被駭風險。
- 冷錢包：私鑰離線保管，存放大部分資金，動用需人工介入。
- 歸集：用戶充值地址收到的資金會定期集中搬移至熱／冷錢包統一管理，否則資金分散於大量地址，出金時無法湊足所需數量。歸集本身也是鏈上轉帳，需支付手續費。

詳見 `06-2` §4。

## 二、開發方規格

> 對應 app：`member`　新增 model：`DepositAddressModel`

### 1. 內部帳本

`WalletModel` 在範圍二不變動，`available` / `frozen` 的語意、不變量與鎖策略維持範圍一設計。真正的鏈上資產不在 `WalletModel`，`WalletModel` 為內部帳本（IOU）。`UserProfileModel.address` 為住址欄位，與鏈上地址無關，不得混用。

### 2. 充值地址（`DepositAddressModel`）

#### 2.1 資料模型

| 欄位 | 說明 |
|---|---|
| `user` | FK → User |
| `asset_type` | FK → CurrencyModel（已含 `chain`，見 `01-2` §2） |
| `address` | CharField(100)，unique。鏈上地址 |
| `derivation_index` | 此地址在 HD 派生路徑上的序號 |
| `created_at` | 建立時間 |

約束：`unique_together = (user, asset_type)`——每人每幣一個地址；`address` 全域唯一。

#### 2.2 HD 派生與私鑰不落庫

- 採用 HD Wallet（分層確定性錢包，BIP32/BIP44）：由一組主種子（seed）依派生路徑（例如 `m/44'/60'/0'/0/{index}`）推導出無限多組私鑰／地址；保住 seed 即可隨時重算所有地址的私鑰。
- 資料庫只存 `derivation_index`，私鑰完全不進資料庫。
- 主種子以環境變數或金鑰管理服務（KMS）保管，不得 commit 進版本控制、不得寫死於程式中。

#### 2.3 EVM 相容鏈的地址共用

以太坊、Polygon、BSC、Arbitrum 等 EVM 系鏈地址格式相同，同一地址在這些鏈上皆可收款，但各鏈餘額獨立。可將同一用戶在所有 EVM 鏈共用一個地址處理，比特幣則另成一套。

### 3. 端點

- `GET /api/deposit/address/?asset_type_id=`——取得（或首次派生）當前使用者於指定幣別的充值地址。權限 `IsAuthenticated`，只能取得自己的地址。此端點只回傳地址，不變動任何餘額，為範圍二唯一新增的用戶端入金端點。
- 入帳一律由監聽服務（系統）觸發，無用戶主動入金端點。

### 4. 交易所熱／冷錢包與歸集

- 熱錢包私鑰連網、可自動簽名用於出金，僅放少量資金；冷錢包私鑰離線、放大部分資金，動用需人工。
- 歸集（sweeping）將各充值地址收到的資金定期集中至熱／冷錢包，歸集為鏈上轉帳需付 gas。實作細節見 `06-2` §4。

### 5. 技術約束／注意事項

- `WalletModel` 為內部帳本而非鏈上錢包（私鑰集合），二者不可等同看待。
- 私鑰／主種子不得進入資料庫或版本控制，資料庫僅保存 `derivation_index`。
- `address` 必須全域唯一，避免同一地址被配給兩個用戶而導致入金記錯對象。
- 須實作歸集機制，避免資金分散於各充值地址、致使熱錢包無法湊足出金數量。
- 須防範送錯鏈：跨不同鏈系（如將 Tron USDT 轉入 EVM 地址）的轉帳會導致資產永久遺失，前端須強制用戶選擇網路並提出警告。
