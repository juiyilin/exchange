# 細部規格 — 撮合引擎（matching engine）〔範圍一〕

> 上層文件：`00_overall_spec.md`　相關：`03-1_order_spec.md`、`05-1_settlement_spec.md`
>
> 範圍二（測試鏈）無對應檔案：本模組在範圍二完全不變。撮合是內部訂單簿的配對，不上鏈、不涉私鑰、不需確認數；鏈只負責入金／出金兩端，中間的買賣不上鏈。

## 一、需求方規格

### 1. 模組職責

從尚未成交的訂單中，找出可配對的買單與賣單，將其撮合為「成交」，並觸發後續結算（結算規則見 `05`）。

### 2. 訂單簿與成交條件

訂單簿是某個交易對上所有未成交掛單的集合，分為兩邊：

- 賣方掛單（想賣的人），由低價到高價排列，最低價為最佳賣價。
- 買方掛單（想買的人），由高價到低價排列，最高價為最佳買價。

當「最高買價 ≥ 最低賣價」時即可撮合。例：有人願買至 30000、有人只要 29950，出價重疊，可成交。

### 3. 成交價：採 maker 定價

成交價一律採用「先掛在簿上那一張單（maker，掛單者）」的價格。若賣單 @29950 先掛在簿上，之後買單 @30000 進來吃它，成交價為 29950（買方享有較優價格）。此規則確保先掛單的一方不會因對手方的出價而吃虧或佔便宜。

### 4. 撮合優先順序：價格優先、時間其次

1. 價格優先：買單出價越高越先成交；賣單要價越低越先成交。
2. 時間其次：同價格下，先掛的先成交（先進先出）。

### 5. Maker / Taker

- Maker（掛單者）：掛在簿上等待被撮合的單，提供流動性。
- Taker（吃單者）：新進場並立即與簿上單成交的單，消耗流動性。

（未來可對 taker 與 maker 採不同費率，屬進階的手續費設計。）

### 6. 部分成交

撮合不保證單次全部吃完。若買方欲買 2 單位、簿上最佳賣單僅有 0.8 單位，先成交 0.8，買單剩餘 1.2 繼續向下一張賣單配對；若無對手可配，剩餘量留在簿上，狀態為「部分成交」。完全吃完則狀態為「全部成交」。

### 7. 自我成交防護與公平性期望

- 撮合須維持價格時間優先的公平性：不得讓後掛的同價單插隊到先掛單之前。
- 每次成交產生的資產移轉結果須正確反映在雙方帳戶：買方付出計價資產、取得標的資產；賣方相反。以 maker 價計算移轉金額。
- 一張大單可對應多筆成交；各筆成交量加總不得超過該單的委託量。

### 8. 需求方驗收情境

- A 掛賣 1 單位 @ 30000；B 掛買 1 單位 @ 30000 → 產生一筆成交，兩張單皆全部成交，雙方餘額正確結算。
- A 掛賣 1 單位 @ 30000；B 掛買 0.4 單位 @ 30000 → 成交 0.4，B 全部成交、A 部分成交，A 剩餘 0.6 留在簿上。

## 二、開發方規格

> 對應 app：`transaction`　主要 model：`OrderModel`、`TransactionModel`

### 1. 撮合演算法（核心流程）

當一張新單（taker）進來，或需撮合整個簿時，對一張要撮合的買單 B（價格 Pb、待成交量 Qb）：

```
1. 找出對手方賣單中「價格 <= Pb」者，依「價格最低、時間最早」排序。
2. 逐一配對：
     取對手賣單 S（價格 Ps、待成交量 Qs）
     成交量 = min(Qb 待成交, Qs 待成交)
     成交價 = maker（先掛者）的價格
     → 建立一筆成交（買單、賣單、成交量、成交價）
     → 觸發結算（見 05）：搬動雙方凍結／可用餘額
     → 更新兩張單的狀態（FILLED 或 PARTIALLY_FILLED）
     Qb -= 成交量
     若 Qb == 0：買單完全成交，結束
3. 若掃完對手方 Qb 仍 > 0：買單剩餘留在簿上等待（PENDING / PARTIALLY_FILLED）
（賣單進來時邏輯對稱）
```

「待成交量」由 `OrderModel.waiting_transaction_quantity()` 求得（委託量 − 已成交量）。每撮合一筆須即時反映到已成交量，否則同一張單會被重複配對到超量。

### 2. 資料模型：成交（`TransactionModel`）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `transaction_number` | CharField(32), unique | 成交代號 |
| `buy_order` | FK → OrderModel (related_name=buy_transactions) | 買單 |
| `sell_order` | FK → OrderModel (related_name=sell_transactions) | 賣單 |
| `quantity` | Decimal(20,2) | 成交數量 |
| `price` | Decimal(20,2) | 成交價格 |

每撮合一次即產生一筆 `TransactionModel`；一張大單可對應多筆成交。

### 3. 分層與非同步任務

核心邏輯 `match_order`／`cancel_order` 置於 `transaction/services.py`，為同步純函式，單元測試直接呼叫。`transaction/tasks.py` 僅放背景非同步處理的進入點 `send_to_match_market`（`@shared_task` 薄殼，轉呼叫 services）。

- 撮合走背景非同步處理：下單負責「驗證＋凍結＋存單」，隨後將撮合工作交付背景佇列，API 立即回應「訂單已建立」，由背景 worker 完成撮合。
- 取消訂單維持同步：view 直接呼叫 `cancel_order` service。

單一真相來源：撮合與取消的核心邏輯須抽為可重用函式，view 僅為薄殼，併發測試亦直接呼叫該函式，避免測試複製 view 邏輯而測到非線上程式碼。

### 4. 併發與原子性

兩個核心威脅：

1. 超賣／雙花：同一錢包餘額被兩個操作同時讀到舊值、各自扣減、互相覆蓋，導致扣兩次僅生效一次、餘額變負。
2. 雙重撮合：同一張單被兩個撮合流程同時取用配對，成交量加總超過其委託量。

防護手段：

- `select_for_update()`：撮合時鎖住相關訂單列與錢包列，其他交易須待鎖釋放。
- `transaction.atomic()`：一筆成交牽涉「建立 Transaction ＋ 改買方兩個錢包 ＋ 改賣方兩個錢包 ＋ 改兩張單狀態」，全部包在同一 atomic，全成功或全 rollback。
- 撮合序列化：同一交易對的撮合同時只允許一個流程進行（以交易對列作為序列化閘門，或讓同一交易對的撮合任務排進同一條佇列）。
- 驗證不變量：每次結算後餘額不得為負（見 `02-1` 不變量），可加 assert 或 DB check constraint。

### 5. 鎖順序鐵則

任何會寫入訂單簿的流程，一律照下列順序取鎖：

```
TradingPair（閘門） → Order（訂單列） → Wallet（錢包列）
```

- deadlock 的成因是兩條流程以相反順序爭搶同一組資源而互等成環。全系統統一取鎖順序，即可在架構上排除環路。
- 以交易對列作為序列化閘門，且必須在鎖任何訂單之前取得；順序反了則失效。不同交易對之間仍可平行。此閘門避免買賣兩邊同時撮合時「先鎖自身訂單、再搶對手訂單」造成的互鎖。

本鐵則適用於所有訂單簿寫入者，不只 `match_order`：

| 流程 | 依序取 |
|---|---|
| `match_order` | pair → taker/maker 訂單 → 錢包 |
| 取消訂單 | pair → 該訂單 → 錢包 |

取消訂單的取鎖細節：須先知道訂單所屬交易對才能鎖 pair，但不可先鎖訂單（否則順序反）。做法為先不加鎖讀出 `trading_pair_id`，用它鎖 pair，再以 `select_for_update` 鎖訂單並重新檢查狀態與擁有權。此不加鎖的預讀是安全的，因為 `trading_pair` 建立後永不改變，僅用於決定「鎖哪一列」，授權與狀態判斷都在取得鎖之後才進行。

### 6. 錢包變動採 `F()` 相對運算

錢包列不受交易對閘門保護：同一錢包可能被其他交易對的撮合（例如 BTC/USDT 與 ETH/USDT 共用同一個 USDT 錢包）或出入金流程同時碰觸，而這些流程並不持有本 pair 的鎖。

因此錢包餘額變動一律採 `F()` 相對運算（`F('x') - n`），交由 DB 端計算，免鎖亦不掉更新。

- 不可為取得 `balance_after` 而將 `F()` 改回「讀-改-寫」，該寫法在跨交易對／出入金併發下會掉更新。
- 若需取變動後餘額，正解為 `.update()` 後重新讀取（見 `07-1` §6.1）。

### 7. 技術約束／注意事項

- 成交價固定採 maker 價，不得採 taker 價，否則先掛單一方會吃虧或佔便宜。
- 每撮一筆須即時更新已成交量，避免同一張單被重複配對到超量。
- 狀態機不得跳錯：部分成交進 `PARTIALLY_FILLED`，僅完全成交才進 `FILLED`。
- 改動餘額前必須依鎖順序取鎖或採 `F()`；未加保護的餘額變動在低量下不易顯現，量大時即出錯。

### 8. 進階方向

- 併發壓力測試（同時投入大量對手單，驗證無超賣、無雙重撮合）。
- 市價單撮合。
- 手續費（maker／taker 不同費率，自成交中抽成進手續費帳戶）。
- 最新成交價、24h 成交量、K 線聚合。
