# 細部規格 — 撮合引擎（matching engine）〔範圍一〕

> 對應 app：`transaction`　主要 model：`OrderModel`、`TransactionModel`
> 上層文件：`00_overall_spec.md`　相關：`03-1_order_spec.md`、`05-1_settlement_spec.md`
>
> **範圍二（測試鏈）無對應檔案，因為本模組在範圍二完全不變。**
> 撮合純粹是內部訂單簿的配對，不上鏈、不碰私鑰、不需要確認數。
> 真實交易所也是如此——鏈只負責入金/出金兩端，中間的買賣**根本不上鏈**
> （不然每秒幾十萬筆交易鏈撐不住）。這正是 CEX 存在的理由。
> （撮合真正的下一個大階段是 DEX 化：屆時撮合搬到智能合約，另立規格。）

這是整個交易所的心臟。把它做對、做穩，你就懂了交易所最核心的東西。

## 1. 這個模組負責什麼

從還沒成交的訂單裡，找出能配對的買單和賣單，把它們撮合成「成交」，並觸發結算（結算的細節在 `05`）。

## 2. 概念

### 訂單簿（Order Book）
某個交易對上所有未成交掛單的集合，分兩邊：

```
            BTC/USDT 訂單簿
   賣單（ASK，想賣的人）        ← 由低到高排，最低價在最前
   ┌──────────────────────┐
   │ 30200  × 0.5          │
   │ 30100  × 1.2          │
   │ 30050  × 0.8          │ ← 最佳賣價（best ask）
   ├──────────────────────┤   ← 中間的價差叫 spread
   │ 30000  × 1.0          │ ← 最佳買價（best bid）
   │ 29900  × 2.0          │
   │ 29800  × 0.5          │
   └──────────────────────┘
   買單（BID，想買的人）        ← 由高到低排，最高價在最前
```

### 什麼時候能成交
**當最高買價 ≥ 最低賣價時**，就能撮合。
例：有人掛買 @ 30000、有人掛賣 @ 29950。買方願付到 30000、賣方只要 29950，重疊了，成交。

### 成交價怎麼定
通常用**先掛單那方的價格**（price-time priority 的自然結果）。如果賣單 @29950 先掛在簿上，後來買單 @30000 進來吃它，成交價是 29950（買方還賺到 50）。v0.1 採「掛在簿上那張（maker）的價格」。

### 撮合優先順序：價格優先、時間其次（Price-Time Priority）
1. **價格優先**：買單出價越高越先成交；賣單要價越低越先成交。
2. **時間其次**：同價格下，先掛的先成交（FIFO）。

### Maker / Taker
- **Maker（掛單者）**：掛在簿上等別人來吃的單，提供流動性。
- **Taker（吃單者）**：新進來、立刻和簿上的單成交的單，消耗流動性。
（手續費常對 taker 收較多、對 maker 收較少甚至給回饋——這是進階的手續費設計。）

## 3. 撮合演算法（核心流程）

當一張新單（taker）進來，或我們要撮合整個簿時：

```
對一張要撮合的買單 B（價格 Pb、待成交量 Qb）：
  1. 找出對手方賣單裡「價格 <= Pb」的，依「價格最低、時間最早」排序
  2. 逐一配對：
       取對手賣單 S（價格 Ps、待成交量 Qs）
       成交量 = min(Qb 待成交, Qs 待成交)
       成交價 = maker（先掛者）的價格
       → 建立一筆 TransactionModel(buy_order=買單, sell_order=賣單, quantity=成交量, price=成交價)
       → 觸發結算（見 05）：搬動雙方凍結/可用餘額
       → 更新兩張單的 status（FILLED 或 PARTIALLY_FILLED）
       Qb -= 成交量
       若 Qb == 0：買單完全成交，結束
  3. 若掃完對手方 Qb 仍 > 0：買單剩餘留在簿上等待（PENDING / PARTIALLY_FILLED）
（賣單進來時邏輯對稱）
```

「待成交量」就是 `OrderModel.waiting_transaction_quantity()`（`quantity - 已成交`）。

### 部分成交（Partial Fill）
撮合不保證一次吃完。買單要 2 BTC、簿上最佳賣單只有 0.8 BTC，就先成交 0.8，買單剩 1.2 繼續找下一張賣單；找不到就留 1.2 在簿上，狀態 `PARTIALLY_FILLED`。

## 4. 資料模型：成交（TransactionModel，現況）

| 欄位 | 型別 | 說明 |
|---|---|---|
| `transaction_number` | CharField(32), unique | 成交代號 |
| `order1` | FK → Order (related_name=buy_order) | 買單 |
| `order2` | FK → Order (related_name=sell_order) | 賣單 |
| `quantity` | Decimal(20,2) | 成交數量 |
| `price` | Decimal(20,2) | 成交價格 |

每撮合一次就產生一筆 TransactionModel。一張大單可能對應多筆成交。

## 5. 同步 vs 非同步（Celery）— 兩階段做法

### 階段一（基本，建議先做）：同步撮合
下單成功後，**在 request 裡直接呼叫撮合函式**跑完再回應。
- 優點：好除錯，邏輯一條線、斷點好設、錯誤直接看得到。
- 缺點：下單 API 會等撮合跑完才回，量大時慢。
- 做法：把撮合邏輯寫成一個獨立函式（例如 `transaction/tasks.py` 的 `send_to_match_market`，現況是空殼），下單流程最後同步呼叫它。

### 階段二（進階）：非同步撮合
下單只負責「驗證+凍結+存單」，然後 `send_to_match_market.delay()` 丟給 Celery，API 立刻回「訂單已建立」。Celery worker 在背景撮合。
- 優點：API 秒回，符合真實架構。
- 缺點：要顧 Celery/Redis 環境、除錯較麻煩、要處理「同一交易對同時被多個 worker 撮合」的併發問題。

> 現況：`exchange/celery.py` 已設定好、`pyproject.toml` 已裝 celery/redis/django-celery-beat/results，`send_to_match_market` 已建好空函式、下單裡的 `.delay()` 呼叫被註解。基礎打好了，先用同步把邏輯做對，再打開非同步。

## 6. 併發與原子性（進階，但要早點理解）

撮合是最容易出併發 bug 的地方。兩個核心威脅：

1. **超賣 / 雙花**：同一個錢包的餘額被兩個操作同時讀到舊值、各自扣、互相覆蓋，結果扣兩次只生效一次，餘額變負。
2. **雙重撮合**：同一張賣單被兩個撮合流程同時拿去配對，成交量加起來超過它的數量。

防法：
- **`select_for_update()`**：撮合時鎖住相關的訂單列和錢包列，其他交易要等鎖釋放。下單那段已示範鎖錢包。
- **`transaction.atomic()`**：一筆成交牽涉「建 Transaction + 改買方兩個錢包 + 改賣方兩個錢包 + 改兩張單狀態」，全部包在同一個 atomic，要嘛全成功要嘛全 rollback。
- **撮合序列化**：同一個交易對的撮合最好一次只有一個流程在跑（例如用鎖、或讓同一交易對的撮合任務排進同一條 Celery 佇列）。
- **驗證不變量**：每次結算後，餘額不該變負（見 `02-1` 的不變量）。可加 assert 或 DB check constraint。

### 6.1 鎖順序鐵則（M6 實作後定案）

> **任何會動到訂單簿的流程，一律照這個順序取鎖：**
>
> ```
> TradingPair（閘門） → Order（訂單列） → Wallet（錢包列）
> ```

**為什麼順序如此重要**：deadlock 的成因永遠是「**兩條流程以相反順序爭搶同一組資源**」——
T1 抓了 A 要 B、T2 抓了 B 要 A，互等成環。只要**全系統都照同一個順序**取鎖，就在架構上不可能繞環。

**為什麼閘門是交易對**：M6 踩過的真實坑——只鎖訂單時，買賣兩邊同時撮合會「先鎖自己的單、再搶對手單」
互鎖成環，PostgreSQL 直接報 `deadlock detected`。解法是**進撮合前先鎖交易對列**當序列化閘門，
且**必須在鎖任何訂單之前**，順序反了就無效。不同交易對之間仍可平行。

**這條鐵則適用於所有訂單簿寫入者，不只 `match_order`**：

| 流程 | 必須依序取 |
|---|---|
| `match_order` | pair → taker/maker 訂單 → 錢包 |
| **取消訂單** | **pair → 該訂單 → 錢包** |

> **取消要先鎖 pair 的實作細節**：你得先知道這張單屬於哪個交易對，才能鎖它——
> 但又不能先鎖訂單（順序就反了）。解法：**先「不鎖」讀出 `trading_pair_id`**，
> 拿它鎖 pair，**再**用 `select_for_update` 鎖訂單並**重新檢查**狀態與擁有權。
> 這個不鎖的預讀是安全的，因為 `trading_pair` 建立後永不改變——它只用來決定「要鎖哪一列」，
> 真正的授權與狀態判斷都在鎖到之後才做。

**單一真相來源**：取消的核心邏輯要抽成一個**可重用函式**（例如 `cancel_order(order_id, user)`），
view 只是薄殼、併發測試也直接呼叫它。否則測試會複製一份 view 的邏輯，
**測到的是複製品、不是真正跑在線上的程式碼**——實作改了測試卻不會紅，等於白測。
（`match_order` 本來就是這樣的純函式，`cancel_order` 與它作伴。）

### 6.2 為什麼錢包不靠鎖、而靠 `F()`

錢包列**不由交易對閘門保護**——同一個錢包可能被「別的交易對的撮合」（例如 BTC/USDT 與 ETH/USDT
共用同一個 USDT 錢包）或「出入金」同時碰到，那些流程根本不持有這個 pair 的鎖。

所以錢包的餘額變動一律用 **`F()` 相對運算**（`F('x') - n`），讓 DB 端自己算，
**免鎖也不會掉更新**。這是 M6 把 `release_frozen` 從「讀-改-寫」改成 `F()` 的原因。

> 不要為了拿 `balance_after` 就把 `F()` 改回「讀-改-寫」——那會在跨交易對／出入金的併發下掉更新。
> 正解是 `.update()` 之後**重新讀**（見 `07-1` §6.1）。

## 7. 基本階段：你要完成的事

1. 把撮合寫成一個獨立函式（先同步），輸入一張新單，找對手撮合。
2. 實作價格時間優先的對手查詢（買單找價格 ≤ 自己的賣單、依價格升序+時間升序）。
3. 逐筆配對、算成交量（min）、建 TransactionModel、更新雙方訂單狀態。
4. 撮合後呼叫結算（見 `05`）搬餘額。
5. 處理部分成交。

**驗證方式**：
- 用戶 A 掛賣 1 BTC @ 30000；用戶 B 掛買 1 BTC @ 30000 → 產生一筆成交，兩張單都 FILLED，餘額正確結算。
- A 掛賣 1 BTC @ 30000；B 買 0.4 BTC @ 30000 → 成交 0.4，B 的單 FILLED、A 的單 PARTIALLY_FILLED，A 還剩 0.6 在簿上。

## 8. 進階階段：逐步加深

- 搬到 Celery 非同步。
- 併發壓力測試（同時丟大量對手單，驗證沒超賣、沒雙重撮合）。
- 市價單撮合。
- 手續費（maker/taker 不同費率，從成交中抽成進手續費帳戶）。
- 最新成交價、24h 成交量、K 線聚合。

## 9. 常見坑

- **成交價用錯**：用 taker 的價而非 maker 的價，會讓先掛單的人吃虧或佔便宜。固定用 maker 價。
- **忘記更新待成交量就重複撮合**：每撮一筆要即時反映到「已成交量」，否則同一張單會被重複配對到超量。
- **狀態機跳錯**：部分成交要進 PARTIALLY_FILLED 而不是直接 FILLED；完全成交才 FILLED。
- **沒鎖就改餘額**：見第 6 節，這是最隱蔽也最致命的 bug，量小時測不出來、上量就爆。
