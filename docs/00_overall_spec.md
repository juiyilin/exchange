# 虛擬貨幣交易所 — 整體規格文件

> 版本：v0.1　範圍：純內部帳本（模擬），文件預留通往「測試鏈入金/出金」的升級路徑
> 技術棧：Python / Django 4.2 / Django REST Framework / Celery / Redis / PostgreSQL

這份文件是整個專案的「地圖」。它告訴你：我們在做什麼、做到什麼程度、系統長什麼樣、有哪些模組、每個模組的細部規格在哪個檔案。細節都在各自的子文件裡，這裡只給全貌。

## 1. 這個專案是什麼

我們要做一個**中心化虛擬貨幣交易所（CEX）的後端**。使用者可以：

- 持有不同幣別的餘額（例如 USDT、BTC）
- 下單買賣（例如「用 USDT 買 BTC」）
- 由系統自動撮合買賣雙方的訂單
- 撮合成交後，雙方餘額自動結算

「中心化」的意思是：所有餘額和訂單都記在**我們自己的資料庫**裡，不是記在區塊鏈上。使用者之間的買賣，本質上是我們資料庫裡數字的搬移。這就是「內部帳本（internal ledger）」。

現實世界的交易所（Binance、Coinbase）核心也是這樣運作的——鏈只負責「把幣搬進交易所」和「把幣搬出交易所」這兩端，中間的買賣撮合完全在交易所自己的資料庫裡發生，根本不上鏈（不然每秒幾十萬筆交易鏈根本撐不住）。

### 範圍邊界（v0.1 我們做什麼、不做什麼）

| 做                                      | 暫不做（但預留升級路徑） |
| --------------------------------------- | ------------------------ |
| 幣別管理                                | 真實區塊鏈節點           |
| 用戶與內部錢包（餘額帳本）              | KYC 身分驗證             |
| 下單（限價單）                          | 法幣通道（刷卡、銀行）   |
| 撮合引擎（價格時間優先）                | 冷熱錢包分離、風控       |
| 成交與結算                              | 真實主網入金/出金        |
| 入金/出金（**模擬**：後台手動加減數字） | —                        |

「升級路徑」指的是：入金/出金模組會設計成一個獨立接口，現在用「後台手動加數字」實作，未來要接測試鏈時，只換掉那一塊的實作，其他模組不動。詳見 `06_deposit_withdraw_spec.md`。

## 2. 名詞解釋（先把這幾個搞懂，後面才看得懂）

- **幣別 / 資產（Currency / Asset）**：一種可以持有的東西，例如 USDT、BTC、ETH。每種幣有代碼（code，如 `BTC`）和名稱（name，如 `Bitcoin`）。
- **交易對（Trading Pair）**：兩種幣的買賣組合，例如 `BTC/USDT` 表示「用 USDT 買賣 BTC」。前面的 `BTC` 叫**標的幣 / 基礎幣（base）**，後面的 `USDT` 叫**計價幣（quote）**。價格的意思是「1 顆 BTC 值多少 USDT」。
- **內部帳本（Internal Ledger）**：我們資料庫裡記錄「誰有多少哪種幣」的那張表，就是 `WalletModel`。
- **可用餘額 / 凍結餘額（available / frozen balance）**：你掛了一張買單還沒成交時，要先買的錢不能被你拿去做別的事，所以從「可用」搬到「凍結」。成交後從凍結扣掉、把買到的幣加進可用。
- **訂單（Order）**：使用者的買賣意圖，例如「我要用 30000 USDT 買 1 BTC」。
- **訂單簿（Order Book）**：某個交易對上，所有還沒成交的買單和賣單的集合。買單由高到低排、賣單由低到高排。
- **撮合（Matching）**：把能成交的買單和賣單配對起來的過程。例如有人想用 30000 買、有人想用 29999 賣，這兩張就能撮合。
- **成交 / 交易（Trade / Transaction）**：一次撮合的結果，記錄「哪張買單和哪張賣單、以什麼價格、成交多少數量」。
- **限價單（Limit Order）**：指定價格的單，「最多 30000 買」或「最少 29000 賣」。v0.1 只做這種。
- **市價單（Market Order）**：不指定價格、用當前市場最好價立刻成交的單。列為進階功能。

## 3. 系統架構

```
                 ┌─────────────────────────────┐
   使用者 ─────▶ │   Django REST API (同步)     │
   (前端/Postman) │  下單、查餘額、查訂單、查成交  │
                 └──────────────┬──────────────┘
                                │ 下單時：驗證 + 凍結餘額 + 存訂單
                                │ 然後丟一個任務到佇列
                                ▼
                 ┌─────────────────────────────┐
                 │      Redis（訊息佇列）        │
                 └──────────────┬──────────────┘
                                │
                                ▼
                 ┌─────────────────────────────┐
                 │   Celery Worker（非同步）     │
                 │   撮合引擎：配對買賣單、       │
                 │   產生成交、結算雙方餘額       │
                 └──────────────┬──────────────┘
                                │ 讀寫
                                ▼
                 ┌─────────────────────────────┐
                 │      PostgreSQL（資料庫）     │
                 │  Currency / Wallet / Order / │
                 │  Transaction                 │
                 └─────────────────────────────┘
```

**為什麼撮合要丟到 Celery（非同步）？**
下單的 API 要回得快——使用者按下「買」應該立刻得到「訂單已建立」的回應，不該卡著等撮合。撮合是後台的事，可能要掃整個訂單簿、可能要連續成交好幾筆，放到背景的 Celery worker 慢慢做，API 就能秒回。這也是現實交易所的做法：下單和撮合是分開的兩件事。

> v0.1 的簡化：初期撮合可以先寫成「同步」直接在下單時跑（方便除錯），等核心穩了再搬到 Celery。這在 `04_matching_engine_spec.md` 會說明兩種做法的取捨。

## 4. 模組（Django App）拆分

專案已經分好四個 app，這個結構很合理，我們沿用：

| App           | 職責                     | 主要 Model                        | 細部規格文件                                                              |
| ------------- | ------------------------ | --------------------------------- | ------------------------------------------------------------------------- |
| `common`      | 共用基底與工具           | `BaseTimeModel`（建立/更新時間）  | （無，跨模組共用）                                                        |
| `currency`    | 幣別與交易對             | `CurrencyModel`                   | `01_currency_spec.md`                                                     |
| `member`      | 用戶、個人資料、錢包帳本 | `UserProfileModel`、`WalletModel` | `02_member_wallet_spec.md`                                                |
| `transaction` | 訂單、撮合、成交         | `OrderModel`、`TransactionModel`  | `03_order_spec.md`、`04_matching_engine_spec.md`、`05_settlement_spec.md` |

入金/出金目前散在 `member`，文件上獨立成 `06_deposit_withdraw_spec.md`，未來可能抽成自己的 app。

### 模組相依關係

```
common  ←─── 所有人都依賴它（時間戳記、工具函式）
currency ←── member(錢包要指定幣別)、transaction(訂單要指定幣別)
member  ←─── transaction(下單要檢查並凍結錢包餘額)
```

依賴方向是單向的（transaction 依賴 member，member 不依賴 transaction），這很重要——避免循環依賴。

## 5. 功能總表

下面是完整功能清單，標好優先級。「基本」是 v0.1 必做、也是我們接下來引導你逐一完成的；「進階」是核心穩了之後再逐步加深。

### 幣別（currency）

- 【基本】新增/查詢幣別
- 【基本】交易對的概念與驗證（currency1 ≠ currency2）
- 【進階】交易對獨立成 model（設定最小下單量、價格精度、手續費率）
- 【進階】幣別啟用/停用

### 用戶與錢包（member）

- 【基本】建立用戶、用戶個人資料
- 【基本】錢包：每人每幣一個，含可用餘額/凍結餘額
- 【基本】查詢自己的錢包餘額
- 【進階】真實認證（取代目前的「隨機指派用戶」）：註冊、登入、Token 驗證
- 【進階】帳本流水（ledger entry）：每筆餘額變動都留一筆不可刪的紀錄

### 訂單（transaction / order）

- 【基本】下限價單（買/賣），下單時檢查並凍結餘額
- 【基本】查詢訂單、訂單狀態（等待中/部分成交/全部成交/已取消）
- 【基本】計算已成交數量、待成交數量
- 【進階】取消訂單（解凍剩餘凍結餘額）
- 【進階】市價單
- 【進階】訂單簿快照 API（給前端畫深度圖）

### 撮合與成交（transaction / matching）

- 【基本】撮合引擎：價格時間優先，配對買賣單
- 【基本】成交後結算雙方餘額（凍結扣減、可用增加）
- 【基本】部分成交處理
- 【進階】搬到 Celery 非同步執行
- 【進階】併發安全（select_for_update、避免雙重撮合）
- 【進階】最新成交價、成交歷史、K 線資料

### 入金/出金（deposit / withdraw）

- 【基本】模擬入金（後台手動加數字到可用餘額）
- 【基本】模擬出金（扣減可用餘額）
- 【進階・升級到範圍2】接測試鏈：產生地址、監聽鏈上到帳、確認數、簽署出金交易

## 6. 開發里程碑（Milestones）

我們會照這個順序引導你做。每個里程碑都是「能跑起來、能驗證」的一小步。

- **M0 — 環境就緒**：能 `runserver`、能進 admin、能跑 migration。（你目前已大致到這）
- **M1 — 幣別與錢包**：建幣別、建用戶錢包、查餘額。資料準備好。
- **M2 — 下單與凍結**：能下限價單，餘額正確凍結；不足時擋下。（你目前已有雛形）
- **M3 — 撮合與結算（同步版）**：下單後立刻撮合，成交後雙方餘額正確結算。**這是整個專案的核心高潮。**
- **M4 — 訂單生命週期**：取消訂單、部分成交、狀態機完整。
- **M5 — 非同步化**：撮合搬到 Celery，API 秒回。
- **M6 — 併發安全**：壓力測試下不會超賣、不會雙重撮合。
- **M7（升級）— 測試鏈入金/出金**：進入範圍 2。

每個里程碑的詳細待辦在 `TASKS.md`，那份是「可接手清單」——下次開新對話時，看那份就知道做到哪、接下來做什麼。
