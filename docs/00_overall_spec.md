## 一、需求方規格

### 1. 專案定位

本專案提供一個**中心化虛擬貨幣交易所（CEX）的後端服務**。對外提供的核心能力為：

- 持有不同幣別的餘額（例如 USDT、BTC）
- 下單買賣（例如「用 USDT 買 BTC」）
- 由系統自動撮合買賣雙方的訂單
- 撮合成交後，雙方餘額自動結算

「中心化」指所有餘額與訂單皆由交易所自身帳務系統記錄，而非記錄於區塊鏈上。使用者之間的買賣，本質上是交易所內部帳本上數字的搬移。此為「內部帳本（internal ledger）」模式，亦即真實交易所的核心運作方式——區塊鏈僅負責資產進出交易所兩端，中間的買賣撮合完全發生在交易所內部帳務。

### 2. 名詞定義

- **幣別 / 資產**：一種可持有的資產，例如 USDT、BTC、ETH。每種幣有代碼與名稱。
- **交易對**：兩種幣的買賣組合，例如「BTC/USDT」表示「用 USDT 買賣 BTC」。前者為標的幣 / 基礎幣（base），後者為計價幣（quote）；價格意義為「一單位基礎幣值多少計價幣」。
- **內部帳本**：記錄「誰持有多少何種幣」的帳務資料。
- **可用餘額 / 凍結餘額**：掛出未成交訂單時，需先將對應資產由可用轉為凍結，以免被挪作他用；成交後由凍結扣除、將取得的資產計入可用。
- **訂單**：使用者的買賣意圖，例如「用 30000 USDT 買 1 BTC」。
- **訂單簿**：某交易對上所有未成交買單與賣單的集合。買單由高至低排列，賣單由低至高排列。
- **撮合**：將可成交的買單與賣單配對的過程。
- **成交 / 交易**：一次撮合的結果，記錄配對的買賣單、成交價格與成交數量。
- **限價單**：指定價格的訂單（「最多以某價買」或「最少以某價賣」）。v0.1 僅提供此種。
- **市價單**：不指定價格、以當前市場最佳價立即成交的訂單。列為進階能力。

### 3. 範圍邊界（v0.1）

| 提供                                    | 暫不提供（預留升級路徑） |
| --------------------------------------- | ------------------------ |
| 幣別管理                                | 真實區塊鏈節點           |
| 用戶與內部錢包（餘額帳本）              | 法幣通道（刷卡、銀行）   |
| 下單（限價單）                          | 冷熱錢包分離、風控       |
| 撮合（價格時間優先）                    | 真實主網入金/出金        |
| 成交與結算                              | —                        |
| 入金/出金（模擬：後台手動加減餘額）     | —                        |
| 身分驗證（KYC）                         | —                        |
| 身份組與權限                            | —                        |

入金/出金能力需設計為獨立對外接口：現階段以「後台手動調整餘額」實作，未來接測試鏈時只替換該接口實作，其餘能力不受影響。詳見 `06-1_deposit_withdraw_spec.md`。

### 4. 對外能力總表

分「基本」與「進階」兩級。

**幣別**

- 【基本】新增/查詢幣別
- 【基本】交易對的概念與驗證（同一交易對的兩種幣不得相同）
- 【進階】交易對成為獨立設定項（最小下單量、價格精度、手續費率）
- 【進階】幣別啟用/停用

**用戶與錢包**

- 【基本】建立用戶、用戶個人資料
- 【基本】錢包：每人每幣一份，含可用餘額與凍結餘額
- 【基本】查詢自己的錢包餘額
- 【進階】真實認證：註冊、登入、身分憑證驗證、兩步驟驗證
- 【進階】身份組與權限：依角色決定誰能對哪些資源進行操作（已提供，四角色，詳見 `09-1_permission_spec.md`）
- 【進階】帳本流水：每筆餘額變動皆留存一筆不可刪除的紀錄

**訂單**

- 【基本】下限價單（買/賣），下單時檢查並凍結餘額
- 【基本】查詢訂單與訂單狀態（等待中 / 部分成交 / 全部成交 / 已取消）
- 【基本】計算已成交數量、待成交數量
- 【進階】取消訂單（解凍剩餘凍結餘額）
- 【進階】市價單
- 【進階】訂單簿快照查詢（供前端繪製深度圖）

**撮合與成交**

- 【基本】撮合：以價格時間優先配對買賣單
- 【基本】成交後結算雙方餘額（凍結扣減、可用增加）
- 【基本】部分成交處理
- 【進階】撮合改為背景非同步執行
- 【進階】併發安全（避免超賣與雙重撮合）
- 【進階】最新成交價、成交歷史、K 線資料

**入金/出金**

- 【基本】模擬入金（後台手動將金額加入可用餘額）
- 【基本】模擬出金（扣減可用餘額）
- 【進階・範圍二】接測試鏈：產生地址、監聽鏈上到帳、確認數、簽署出金交易

### 5. 對外行為與驗收條件

- 下單請求需即時回應「訂單已建立」，不因後續撮合處理而延遲；撮合與結算為背景作業。
- 下單時若可用餘額不足以支付訂單所需，訂單須被拒絕，且不得凍結任何餘額。
- 下單成功後，訂單所需資產須由可用餘額轉入凍結餘額。
- 撮合成交後，買賣雙方餘額須自動、正確結算：由凍結扣除、將取得資產計入可用；部分成交時僅結算已成交部分，剩餘部分維持有效。
- 訂單狀態須能正確反映其生命週期（等待中 / 部分成交 / 全部成交 / 已取消）。
- 任何時點下，全體帳本的資產不得因買賣而憑空增減（餘額守恆）。

## 二、開發方規格

### 1. 技術棧

Python / Django 5.2 / Django REST Framework / Celery / Redis / PostgreSQL。

### 2. 系統架構與資料流

```
                 ┌─────────────────────────────┐
   使用者 ─────▶ │   Django REST API (同步)     │
   (前端/Postman) │  下單、查餘額、查訂單、查成交  │
                 └──────────────┬──────────────┘
                                │ 下單時：驗證 + 凍結餘額 + 存訂單
                                │ 然後丟一個任務到佇列
                                ▼
                 ┌─────────────────────────────┐
                 │      Redis（訊息佇列）        │
                 └──────────────┬──────────────┘
                                │
                                ▼
                 ┌─────────────────────────────┐
                 │   Celery Worker（非同步）     │
                 │   撮合引擎：配對買賣單、       │
                 │   產生成交、結算雙方餘額       │
                 └──────────────┬──────────────┘
                                │ 讀寫
                                ▼
                 ┌─────────────────────────────┐
                 │      PostgreSQL（資料庫）     │
                 │  Currency / Wallet / Order / │
                 │  Transaction                 │
                 └─────────────────────────────┘
```

下單 API 與撮合分離：API 於同步請求內完成驗證、凍結餘額與建立訂單後即回應，撮合作業交由背景 Celery worker 執行（可能掃描整個訂單簿並連續成交多筆）。

初期撮合可先以同步方式在下單流程中執行以利除錯，核心穩定後再遷至 Celery；兩種做法的取捨見 `04-1_matching_engine_spec.md`。

### 3. 模組（Django App）劃分

| App           | 職責                         | 主要 Model                                 | 細部規格                                     |
| ------------- | ---------------------------- | ------------------------------------------ | -------------------------------------------- |
| `common`      | 共用基底與工具               | `BaseTimeModel`（建立/更新時間）           | （無，跨模組共用）                            |
| `currency`    | 幣別與交易對                 | `CurrencyModel`                            | `01-1`（範圍二：`01-2`）                       |
| `ledger`      | 帳本流水、入出金紀錄（稽核） | `LedgerEntryModel`、`DepositWithdrawModel` | `07-1`（範圍二：`07-2`）                       |
| `member`      | 用戶、個人資料、錢包帳本     | `UserProfileModel`、`WalletModel`          | `02-1`（範圍二：`02-2`）、入出金端點見 `06-1`  |
| `transaction` | 訂單、撮合、成交             | `OrderModel`、`TransactionModel`           | `03-1`、`04-1`、`05-1`（範圍二無變更）         |

`ledger` 為稽核層：每次錢包餘額變動皆須在同一原子交易內補寫一筆不可變的 `LedgerEntryModel`。入金/出金的業務紀錄 `DepositWithdrawModel` 亦歸於此模組（架構決策見 `07-1_logging_audit_spec.md`）。

### 4. 模組相依關係

```
common  ←─── 所有模組皆依賴（時間戳記、工具函式）
currency ←── ledger / member / transaction 皆需指定幣別
ledger  ←─── member、transaction 在業務函式中寫入帳本流水（import LedgerEntryModel）
member  ←─── transaction（下單需檢查並凍結錢包餘額）
```

完整層次（單向依賴）：

```
common ← currency ← ledger ← member ← transaction
```

### 5. 技術約束與注意事項

- **依賴方向單向**：依賴關係必須保持單向以避免循環依賴。`ledger` 得插於 `currency` 與 `member` 之間，前提是它僅向下依賴 `currency`（`LedgerEntryModel.asset_type` 外鍵指向 `CurrencyModel`），且對訂單/成交僅以軟參照（字串 `ref_type` / `ref_id`）連結、不建立外鍵。若 `ledger` 反向對 `WalletModel` 或 `OrderModel` 建立外鍵，即與 `member` / `transaction` 形成相依環。細節見 `07-1_logging_audit_spec.md` §3.1。
- **餘額變動原子性**：錢包餘額變動與其對應的 `LedgerEntryModel` 補寫須位於同一原子交易內，兩者同成同敗。
- **帳本不可變**：`LedgerEntryModel` 為不可刪除、不可修改的紀錄。
- **入出金接口隔離**：鏈的複雜度須全數封裝於入出金模組（`06-2`）內。`03`（訂單）、`04`（撮合）、`05`（結算）僅操作內部帳本、不感知「鏈」的存在，因此範圍二無需 `-2` 版本、亦無需改動核心。此為 `06-1` 設計原則之延伸。
- **併發安全（進階）**：撮合與結算須以資料庫列鎖（`select_for_update`）等機制避免超賣與雙重撮合。

### 6. 文件命名規則

規格檔名為 `NN-S_模組名_spec.md`：`NN` 為模組編號，`S` 為範圍——`-1` 為範圍一（純內部帳本，不接鏈），`-2` 為範圍二（接測試鏈）。

範圍二設計文件（尚未實作）涵蓋：`01-2`（幣別鏈上屬性、精度 migration）、`02-2`（充值地址 `DepositAddressModel`、HD 派生、熱/冷錢包）、`06-2`（鏈上入金監聽/確認/入帳與鏈上出金扣款/廣播/確認/退款）、`07-2`（狀態機轉移、`tx_hash` 唯一與冪等、反向分錄、鏈上餘額對帳）。
