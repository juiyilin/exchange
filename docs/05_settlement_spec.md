# 細部規格 — 成交結算（settlement）

> 對應 app：`transaction` / `member`　主要 model：`TransactionModel`、`WalletModel`
> 上層文件：`00_overall_spec.md`　相關：`04_matching_engine_spec.md`、`02_member_wallet_spec.md`

## 1. 這個模組負責什麼

撮合決定「誰和誰、成交多少、什麼價」。**結算**負責把這個結果反映到雙方的錢包餘額上——把該扣的扣、該加的加，並維持餘額不變量。撮合和結算通常在同一個 atomic 交易裡完成。

## 2. 一筆成交要搬動哪些餘額

假設一筆成交：買方 B、賣方 S，成交數量 `q` BTC，成交價 `p`（USDT/BTC），總價 `q × p` USDT。

下單時雙方已經各自凍結了該付的幣（見 `03`）：
- 買方 B 早已凍結 USDT（下單時凍結了 `下單量 × 下單價`）。
- 賣方 S 早已凍結 BTC（下單時凍結了 `下單量`）。

成交時的搬動：

| 對象 | 錢包 | 動作 |
|---|---|---|
| 買方 B | USDT 錢包 | `frozen_balance -= q × p`（付出計價幣，從凍結扣） |
| 買方 B | BTC 錢包 | `available_balance += q`（收到標的幣，進可用） |
| 賣方 S | BTC 錢包 | `frozen_balance -= q`（付出標的幣，從凍結扣） |
| 賣方 S | USDT 錢包 | `available_balance += q × p`（收到計價幣，進可用） |

四個錢包改動，加上「建立 TransactionModel」「更新兩張訂單狀態」，全部包在**同一個 `transaction.atomic()`**。

> 注意成交價可能低於買方掛的價（買方撿到便宜）。這時買方凍結的 USDT 會比實際付的多——多凍的部分要在「這張買單完全結束（FILLED 或 CANCELED）」時退回可用。這是結算容易漏的細節，見第 4 節。

## 3. 數值範例

買方 B：有 100000 USDT。掛單買 1 BTC @ 30000 → 凍結 30000 USDT（可用剩 70000）。
賣方 S：有 2 BTC。掛單賣 1 BTC @ 29000 → 凍結 1 BTC（可用剩 1）。

撮合：B 的買價 30000 ≥ S 的賣價 29000，成交。S 先掛 → 成交價用 maker（這裡假設 S 是 maker）= 29000，數量 1。

結算後：
- B 的 USDT：凍結 `30000 - 1×29000 = 1000` 還凍著（多凍的），可用 70000。
- B 的 BTC：可用 `0 + 1 = 1`。
- S 的 BTC：凍結 `1 - 1 = 0`，可用 1。
- S 的 USDT：可用 `0 + 29000 = 29000`。

B 的買單此時 FILLED（要的 1 BTC 拿到了），那多凍的 1000 USDT 要退回 B 的 USDT 可用 → 可用變 71000、凍結變 0。

## 4. 多凍結退款（refund）

只發生在**買單以低於掛價成交**時（賣單不會有這問題，賣單凍的是固定數量的 BTC）。

規則：當一張買單到達終態（FILLED 或 CANCELED），計算它「實際花掉的計價幣」與「當初凍結的計價幣」差額，把差額從凍結退回可用。

實作上可以：
- 每張買單結束時，把它名下 USDT 錢包還凍著、且不再對應任何活躍單的部分，退回可用；或
- 更精準地：追蹤這張單凍了多少、花了多少，結束時退差額。

> 基本階段可以先不處理退款（用「成交價=買單價」的簡化測法，讓多凍=0），把核心撮合結算跑通；進階再補退款邏輯。文件先標記這是已知簡化。

## 5. 基本階段：你要完成的事

1. 寫一個結算函式：輸入一筆成交（買單、賣單、數量、價格），原子地搬動四個錢包餘額。
2. 用 `select_for_update()` 鎖四個錢包再改。
3. 改完後驗證沒有任何餘額變負（不變量）。
4. 和撮合（`04`）串起來：撮合產生成交 → 立刻結算。

**驗證方式**：用第 3 節的數值（但讓買賣同價 30000 避開退款），跑完後四個錢包餘額完全符合手算。

## 6. 進階階段：逐步加深

- 多凍結退款（第 4 節）。
- 手續費：成交時從買方收到的 BTC、賣方收到的 USDT 各抽一小比例進「手續費帳戶」。要決定費率、四捨五入方向（永遠對交易所有利的方向，避免湊出免費套利）。
- 帳本流水（見 `02` 6.2）：每次餘額變動寫一筆 LedgerEntry，結算能完整對帳。
- 對帳工作：定期掃「所有錢包可用+凍結總和」是否守恆，抓出潛在 bug。

## 7. 常見坑

- **凍結扣成負數**：結算扣的凍結量必須來自「這張單當初凍的」，不能多扣。配合撮合的待成交量計算。
- **四個錢包沒一起鎖/一起改**：只改一半就 commit，餘額對不上。務必同一個 atomic。
- **手續費四捨五入漏洞**：捨入方向錯會被人用大量小額單套出免費手續費。捨入永遠不利於用戶、有利於交易所。
- **退款重複退**：同一張買單的多凍結只能退一次，退完要標記，避免取消和成交各退一次。
