# 細部規格 — 入金 / 出金（deposit / withdraw）〔範圍二：測試鏈〕

> 對應 app：`member`、`ledger`、（新增）鏈上監聽服務
> 上層文件：`00_overall_spec.md`　**範圍一前篇：`06-1_deposit_withdraw_spec.md`**
> 相關：`01-2_currency_spec.md`（幣別的鏈上屬性）、`02-2_member_wallet_spec.md`（充值地址）、`07-2_logging_audit_spec.md`（範圍二的紀錄）
>
> **狀態：設計文件，尚未實作。** 這是 CEX 的最後一哩路——把入出金那兩端從「模擬」換成「真的碰鏈」。

## 0. 這一步在改什麼（先看全貌）

**只有「觸發器」和「憑據」變了，入金/出金的核心邏輯完全不變。**

| 面向 | 範圍一（模擬） | 範圍二（測試鏈） |
|---|---|---|
| 誰觸發入帳 | admin 手動呼叫端點 | **鏈上監聽服務**自動偵測到帳 |
| 入帳的依據 | 沒有依據，憑空加數字 | 鏈上真的有一筆轉帳，有憑有據（`tx_hash`） |
| 用戶要做什麼 | 什麼都不用做 | 先取得**充值地址**，再從自己錢包發**鏈上轉帳** |
| `status` | 直接 `DONE` | `PENDING` → `DONE` / `FAILED`（狀態機真的動起來） |
| 耗時 | 毫秒（一次 DB 寫入） | **分鐘級**（等打包 + 等確認數） |
| `tx_hash` / `address` | 留空 | 填入真實鏈上交易雜湊與對方地址 |

**不變的是**：`available += amount` → 建 `DepositWithdrawModel` → 寫 `LedgerEntry` 這段核心（`06-1` §2.3 已抽成函式）。
而更下游的撮合、結算、訂單**完全無感**——它們只看到餘額變大變小，永遠不知道鏈的存在。

## 1. 前置：這一步需要先有什麼

- **幣別的鏈上屬性**（`01-2`）：這個幣在哪條鏈、是原生幣還是代幣、合約地址、`decimals`、要等幾個確認數。
- **充值地址管理**（`02-2`）：每個用戶每個幣一個專屬地址（`DepositAddressModel`），用 HD wallet 派生。
- **節點存取**：自架節點，或用 Infura / Alchemy 之類的 RPC 服務。測試網用 Sepolia（以太）或 Bitcoin testnet。
- **私鑰保管**：熱錢包與 HD 主種子的私鑰，一律走環境變數 / 金鑰管理服務（KMS）。**絕不可 commit 進 git。**

## 2. 入金（鏈上）

### 2.1 流程

1. **用戶取得充值地址**：打 `GET /api/deposit/address/?asset_type_id=`（`IsAuthenticated`）。
   沒有就即時派生一個並存起來（見 `02-2`）。
   **注意：這是範圍二唯一新增的「用戶端」入金 API**——它只給地址，不動餘額。
2. **用戶自己在鏈上轉帳**：從他自己的錢包簽名、把幣送到那個地址。**這一步完全不經過我們的後端。**
3. **監聽服務偵測**：背景任務（輪詢 RPC 或 webhook）盯著所有充值地址。
   看到一筆轉入 → 建一筆 `DepositWithdrawModel(direction=DEPOSIT, status=PENDING, tx_hash=..., address=<來源地址>)`。
   **此時不入帳。**
4. **等確認數**：每產生新區塊就重算該交易的確認數。
   達到該幣的 `min_confirmations`（`01-2`）→ 才呼叫**範圍一那個入金核心函式**入帳，
   並把 `status` 改成 `DONE`、寫 `LedgerEntry(reason=DEPOSIT)`。
5. **失敗**：交易被丟棄 / 因鏈重組而消失 → `status = FAILED`，**不入帳**（本來就還沒入）。

### 2.2 為什麼一定要等確認數

區塊鏈會**分叉重組**：剛進區塊的交易有可能被回滾。若確認數不夠就入帳，攻擊者可以**雙花**——
先轉幣給你、你入帳了、他再讓那筆交易被回滾 → 幣退回他手上，但他已經拿到交易所餘額（甚至已經賣掉、提走）。
**交易所直接虧錢。** 等 N 個確認，就是讓「被回滾」的機率指數級下降。

### 2.3 冪等性（必守）

**同一筆鏈上交易，只能入帳一次。** 監聽服務會重複掃到同一筆交易（輪詢、重啟、重試都會），
若不擋，用戶餘額會憑空多好幾份。

作法：**`tx_hash` 唯一約束**（見 `07-2` §2）。入帳前先查「這個 `tx_hash` 是否已有 `DONE` 的紀錄」，
有就直接跳過。這與撮合的冪等設計是同一個心法（`04-1` M6：`match_order` 要能被重複呼叫而不出錯）。

### 2.4 admin 端點退場

範圍一那個 `POST /api/user/wallet/deposit/`（admin-only）是**鏈上監聽器的替身**，
到這裡它的任務結束，**移除**。入帳改由監聽服務觸發。

## 3. 出金（鏈上）

### 3.1 流程

1. **用戶發起**：`POST /api/user/wallet/withdraw/`，body 多一個 **`address`（外部地址）**——
   範圍一不需要這欄，因為幣沒有真的要送去哪裡。
2. **先扣內部餘額**（atomic）：檢查可用餘額 → `available -= quantity` →
   建 `DepositWithdrawModel(direction=WITHDRAW, status=PENDING, address=<目標地址>)` + 寫 `LedgerEntry(reason=WITHDRAW)`。
   **先扣再送**，否則用戶能在鏈上交易還沒完成時，把同一筆錢又拿去下單或再提一次。
3. **背景任務簽署並廣播**：從**熱錢包**用私鑰簽一筆鏈上交易，送到用戶指定的外部地址。
   拿到 `tx_hash` 就寫回該筆 DW。
4. **等確認** → `status = DONE`。
5. **失敗**（廣播失敗、交易被丟棄）→ `status = FAILED`，並**把餘額退回去**：
   寫一筆**反向 `LedgerEntry`** 把 `available` 加回來（見 `07-2` §3——append-only 的體現：不改舊帳，寫反向分錄）。

### 3.2 出金的冪等性

**同一筆出金絕不能廣播兩次**，否則幣送出去兩份。Celery 是 at-least-once，任務會重送。

作法：廣播前先鎖住該筆 DW（`select_for_update`）並檢查 `status` 仍是 `PENDING`；
已有 `tx_hash` 就代表送過了，直接跳過。以太系還要注意 **nonce 管理**（同一個熱錢包地址的交易序號，
併發簽署容易撞號）。

### 3.3 風控（進階，可選）

大額出金觸發**人工審核**；提幣**地址白名單**；單日限額；新綁定地址冷卻期。
這些都是真實交易所的標配，屬進階。

### 3.4 出金手續費

交易所代為廣播要付 **gas**（鏈上網路費），通常轉嫁給用戶當「提幣手續費」。
這時要在帳本記一筆**獨立的 reason**（例如 `WITHDRAW_FEE` / `NETWORK_FEE`），
**與 `TRADING_FEE`（交易所抽成）分開**——兩者性質完全不同，見 `07-1` §5.1。

## 4. 熱錢包 / 冷錢包

- **熱錢包**：私鑰**連著網路**、能自動簽名。出金必須用它（要能即時簽署廣播）。
  因為連網，被駭風險高 → **只放一小部分資金**。
- **冷錢包**：私鑰**離線保管**（硬體設備、離線電腦）。大部分資金放這裡，安全但動用要人工介入。
- 熱錢包餘額不足時，從冷錢包人工補充（**歸集**）。

這就是「冷熱錢包分離」，`00_overall_spec.md` 的「暫不做」清單裡那項講的就是它。

## 5. 常見坑（範圍二）

- **確認數不夠就入帳** → 鏈重組 / 雙花 → **交易所虧錢**。這是最貴的錯。
- **同一筆鏈上交易入帳兩次** → 用戶餘額憑空多一份。務必靠 `tx_hash` 唯一 + 入帳前檢查。
- **出金重放** → 同一筆出金廣播兩次，幣送出去兩份。鎖 DW + 檢查 `status`/`tx_hash`。
- **精度換算** → 鏈上金額是**整數的最小單位**（wei、satoshi），顯示單位差好幾個數量級
  （ETH 18 位、BTC 8 位）。換算錯會差 10^18 倍。**而且我們現在的 `Decimal(20,2)` 只有 2 位小數，
  範圍二一定不夠用**——這是必須先處理的 migration，見 `01-2` §3。
- **用戶送錯鏈 / 送錯幣** → 例如把 Tron 上的 USDT 轉到以太坊的 USDT 充值地址 → **資產永久遺失**。
  這是真實世界最常見的災難，所以入金介面一定要**逼用戶選網路**並跳警告。
- **私鑰外洩** → 熱錢包私鑰若寫死在程式或 commit 進 git，等於把金庫公開。務必用環境變數 / KMS。
- **監聽服務漏掉區塊** → 重啟後要能從上次處理到的區塊高度接續掃描（記錄 `last_scanned_block`），
  不能只聽「新的」事件。
