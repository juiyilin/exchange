# 細部規格 — 入金 / 出金（deposit / withdraw）〔範圍二：測試鏈〕

> 上層文件：`00_overall_spec.md`　範圍一前篇：`06-1_deposit_withdraw_spec.md`
> 相關：`01-2_currency_spec.md`（幣別的鏈上屬性）、`02-2_member_wallet_spec.md`（充值地址）、`07-2_logging_audit_spec.md`（範圍二的紀錄）

## 一、需求方規格

### 1. 範圍與核心原則

本階段把入金與出金的兩端從「模擬」換成「真的碰鏈」。**核心原則:只更換「觸發器」與「憑據」,入出金的核心邏輯完全不變。**

- 觸發器改變:入帳不再由人工手動觸發,而是由系統偵測到鏈上真實轉帳後自動觸發。
- 憑據改變:每一筆入帳與出金都對應鏈上一筆真實交易,有據可查。
- 不變的部分:餘額增減、記帳與訂單生命週期的核心行為維持原樣;更下游的撮合、結算、訂單對「是否碰鏈」完全無感,它們只看到餘額變大變小。

因為要等待鏈上打包與確認,入金與出金的完成時間從即時變為分鐘級。

### 2. 前置條件

- 幣別需具備鏈上屬性:所在鏈、原生幣或代幣、精度、需等待的確認數等(見 `01-2`)。
- 每個用戶每個幣需能取得一個專屬充值地址(見 `02-2`)。
- 系統需能存取鏈上節點以偵測與廣播交易;測試階段使用測試網。
- 用於自動簽署出金的私鑰須安全保管,不可外流。

### 3. 入金(鏈上)對外行為

1. **取得充值地址**:用戶先向系統索取自己該幣別的專屬充值地址。此動作只提供地址,不改變任何餘額,是本階段唯一新增的用戶端入金動作。
2. **用戶自行轉帳**:用戶從自己的錢包把幣轉入該地址。此步驟完全不經過交易所。
3. **系統偵測到帳**:系統持續監看所有充值地址,偵測到一筆轉入時先建立一筆「等待中」的入金紀錄,**此時尚不入帳**。
4. **等待確認數**:每產生新區塊便重算該筆交易的確認數,達到該幣所需的確認數門檻後才實際入帳、把該筆入金標記為完成並記帳。
5. **失敗處理**:若交易被丟棄或因鏈重組而消失,將該筆入金標記為失敗,不入帳(本就尚未入帳)。

### 4. 確認數的安全意義

區塊鏈可能發生分叉重組,剛進區塊的交易有機會被回滾。若確認數不足即入帳,攻擊者可先轉幣使交易所入帳、再讓該筆交易被回滾,幣退回自己手上卻已取得交易所餘額,造成交易所直接虧損(雙花)。等待足夠的確認數,能讓「被回滾」的機率快速下降,是入金安全的關鍵防線。

### 5. 入金冪等(必守)

**同一筆鏈上交易只能入帳一次。** 系統可能因輪詢、重啟或重試而重複偵測到同一筆交易;若不防範,用戶餘額會憑空多出數份。系統須確保重複偵測到同一筆鏈上交易時只入帳一次。

### 6. 出金(鏈上)對外行為

1. **用戶發起**:用戶提出出金申請,並提供要送達的外部地址(範圍一不需要此資訊,因為並未真的送出)。
2. **先扣內部餘額**:系統先檢查可用餘額並扣除,同時建立一筆「等待中」的出金紀錄並記帳。**必須先扣再送**,否則用戶能在鏈上交易尚未完成前,把同一筆錢再拿去下單或再次提領。
3. **簽署並廣播**:系統以熱錢包簽署一筆鏈上交易,送往用戶指定的外部地址,並在取得鏈上交易憑據後回填至該筆出金紀錄。
4. **等待確認**:達到確認條件後,將該筆出金標記為完成。
5. **失敗退款**:若廣播失敗或交易被丟棄,將該筆出金標記為失敗,並把先前扣除的餘額退回用戶(以反向記帳實現,不修改舊帳)。

### 7. 出金冪等(必守)

**同一筆出金絕不能廣播兩次**,否則幣會被送出兩份。系統須確保同一筆出金只被廣播並送出一次。

### 8. 出金手續費

交易所代為廣播需支付鏈上網路費,通常轉嫁給用戶作為提幣手續費。此費用須在帳本中以獨立的名目記錄,並與交易所交易抽成明確分開,兩者性質不同(見 `07-1` §5.1)。

### 9. 出金風控(進階,可選)

大額出金觸發人工審核、提幣地址白名單、單日限額、新綁定地址冷卻期等,屬真實交易所標配的進階功能。

### 10. 熱錢包 / 冷錢包

- **熱錢包**:私鑰連網、能自動簽名,出金必須使用;因連網風險高,只放一小部分資金。
- **冷錢包**:私鑰離線保管,存放大部分資金,動用需人工介入。
- 熱錢包餘額不足時,由冷錢包人工補充(歸集)。

此即「冷熱錢包分離」,對應 `00_overall_spec.md`「暫不做」清單中的該項。

## 二、開發方規格

> 對應 app:`member`、`ledger`、(新增)鏈上監聽服務

### 1. 範圍一核心邏輯的重用

入帳核心(`available += amount` → 建立 `DepositWithdrawModel` → 寫入 `LedgerEntry`)已在 `06-1` §2.3 抽為函式,本階段直接重用,由監聽服務在確認數達標後呼叫。撮合、結算、訂單邏輯不需任何改動。

| 面向 | 範圍一(模擬) | 範圍二(測試鏈) |
|---|---|---|
| 誰觸發入帳 | admin 手動呼叫端點 | 鏈上監聽服務自動偵測 |
| 入帳依據 | 無,憑空加數 | 鏈上真實轉帳,有 `tx_hash` |
| `status` | 直接 `DONE` | `PENDING` → `DONE` / `FAILED` |
| `tx_hash` / `address` | 留空 | 填入真實鏈上交易雜湊與對方地址 |

### 2. 前置技術依賴

- 幣別鏈上屬性(所在鏈、原生幣/代幣、合約地址、`decimals`、`min_confirmations`)見 `01-2`。
- 每用戶每幣一個 `DepositAddressModel`,以 HD wallet 派生,見 `02-2`。
- 節點存取:自架節點或 Infura / Alchemy 等 RPC 服務;測試網用 Sepolia 或 Bitcoin testnet。
- 私鑰保管:熱錢包與 HD 主種子私鑰一律走環境變數 / KMS,絕不可 commit 進 git。

### 3. 入金流程與狀態機

1. 用戶端取得地址:`GET /api/deposit/address/?asset_type_id=`(`IsAuthenticated`);無地址則即時派生並存下(見 `02-2`)。此為範圍二唯一新增的用戶端入金 API,只給地址、不動餘額。
2. 監聽服務(輪詢 RPC 或 webhook)偵測到充值地址的轉入時,建立 `DepositWithdrawModel(direction=DEPOSIT, status=PENDING, tx_hash=..., address=<來源地址>)`,此時不入帳。
3. 每產生新區塊重算確認數,達到該幣 `min_confirmations` 後呼叫範圍一入金核心函式入帳,將 `status` 改為 `DONE` 並寫 `LedgerEntry(reason=DEPOSIT)`。
4. 交易被丟棄或因鏈重組消失 → `status = FAILED`,不入帳。

### 4. 入金冪等技術約束

以 `tx_hash` 唯一約束(見 `07-2` §2)實作。入帳前先查該 `tx_hash` 是否已有 `DONE` 紀錄,有則跳過。與撮合的冪等心法相同(`04-1` M6:`match_order` 可被重複呼叫而不出錯)。

### 5. admin 端點退場

範圍一的 `POST /api/user/wallet/deposit/`(admin-only)是鏈上監聽器的替身,本階段移除,入帳改由監聽服務觸發。

### 6. 出金流程與狀態機

1. `POST /api/user/wallet/withdraw/`,body 新增 `address`(外部地址)。
2. 於 atomic 交易內檢查可用餘額 → `available -= quantity` → 建 `DepositWithdrawModel(direction=WITHDRAW, status=PENDING, address=<目標地址>)` + 寫 `LedgerEntry(reason=WITHDRAW)`。
3. 背景任務以熱錢包私鑰簽署並廣播,取得 `tx_hash` 後回填該筆 DW。
4. 達到確認條件 → `status = DONE`。
5. 廣播失敗或交易被丟棄 → `status = FAILED`,並寫反向 `LedgerEntry` 把 `available` 加回(見 `07-2` §3,append-only:不改舊帳,寫反向分錄)。

### 7. 出金冪等技術約束

Celery 為 at-least-once,任務會重送。廣播前以 `select_for_update` 鎖住該筆 DW 並檢查 `status` 仍為 `PENDING`;已有 `tx_hash` 即代表送過,直接跳過。以太系另需注意 nonce 管理(同一熱錢包地址的交易序號,併發簽署易撞號)。

### 8. 出金手續費記帳

手續費以獨立 `reason`(例如 `WITHDRAW_FEE` / `NETWORK_FEE`)記於帳本,與 `TRADING_FEE` 分開,見 `07-1` §5.1。

### 9. 技術約束 / 注意事項

- **確認數門檻**:確認數不足即入帳會導致鏈重組 / 雙花與交易所虧損,務必達 `min_confirmations` 才入帳。
- **入金冪等**:靠 `tx_hash` 唯一約束 + 入帳前檢查,避免同一筆鏈上交易入帳兩次。
- **出金重放**:鎖 DW + 檢查 `status` / `tx_hash`,避免同一筆出金廣播兩次。
- **精度換算**:鏈上金額為整數最小單位(wei、satoshi),顯示單位差好幾個數量級(ETH 18 位、BTC 8 位),換算錯會差 10^18 倍。現行 `Decimal(20,2)` 僅 2 位小數,範圍二不敷使用,須先處理 migration,見 `01-2` §3。
- **送錯鏈 / 送錯幣**:跨鏈同名資產(如 Tron USDT 轉入以太 USDT 地址)會永久遺失,入金介面須強制用戶選網路並跳警告。
- **私鑰保管**:熱錢包私鑰不可寫死於程式或 commit 進 git,務必走環境變數 / KMS。
- **監聽續掃**:監聽服務須記錄 `last_scanned_block`,重啟後從上次處理到的區塊高度接續掃描,不可只聽新事件。
