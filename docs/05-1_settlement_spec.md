# 細部規格 — 成交結算（settlement）〔範圍一〕

> 上層文件：`00_overall_spec.md`　相關：`04-1_matching_engine_spec.md`、`02-1_member_wallet_spec.md`
>
> **範圍二（測試鏈）無對應檔案，本模組在範圍二完全不變。** 結算是內部帳本餘額的原子搬移，不涉及簽名、gas 或確認等待；與鏈上轉帳為兩件事，接上測試鏈後結算邏輯無須更動。

## 一、需求方規格

### 1. 本模組的職責

撮合決定「誰和誰、成交多少、什麼價」。結算負責把這個結果反映到買賣雙方的錢包餘額上——該扣的扣、該加的加，並維持餘額不變量。

### 2. 一筆成交的餘額變動

一筆成交涉及買方與賣方，成交有其成交數量與成交價，並可換算出總價（計價幣）。下單時雙方已各自凍結了應付的幣：買方凍結計價幣，賣方凍結標的幣。

成交時，收付雙方共產生四筆餘額變動：

| 對象 | 幣別 | 變動 |
| ---- | ---- | ---- |
| 買方 | 計價幣 | 從凍結扣除已成交部分應付的計價幣（付出計價幣） |
| 買方 | 標的幣 | 可用增加已成交的標的幣（得到標的幣） |
| 賣方 | 標的幣 | 從凍結扣除已成交的標的幣（付出標的幣） |
| 賣方 | 計價幣 | 可用增加已成交部分收到的計價幣（得到計價幣） |

買方付出計價幣（自凍結扣）、得到標的幣（進可用）；賣方相反。

### 3. 部分成交只結算已成交部分

一次結算只搬動「本次成交數量」對應的餘額，未成交的部分仍維持在原本的凍結狀態，等待後續成交或訂單終態處理。

### 4. 結算的全有全無（原子性）

一筆成交所涉及的四筆餘額變動，連同成交紀錄的建立與相關訂單狀態的更新，構成不可分割的整體：要嘛全部生效，要嘛全部不生效。對外不會觀察到「只搬了一半」的中間狀態，也不會出現任一方餘額變負。

### 5. 多凍結退款（refund）

成交價可能優於買方掛單價（買方以低於掛價成交），此時買方下單時凍結的計價幣會多於實際付出的部分。此差額不會在每筆成交時退還，而是在該張買單到達終態（完全成交或已取消）時，一次性把「當初凍結」與「實際花費」的差額從凍結退回可用。

- 只發生於買單以低於掛價成交時；賣單凍結的是固定數量的標的幣，不產生此差額。
- 同一張買單的多凍結差額只退一次。

> 基本階段可採「成交價＝買單價」的簡化情境，使多凍差額為零，先跑通核心結算；退款邏輯於進階階段補上。

### 6. 數值範例

買方 B 有 100000 計價幣，掛單買 1 標的幣 @ 30000，凍結 30000（可用剩 70000）。賣方 S 有 2 標的幣，掛單賣 1 標的幣 @ 29000，凍結 1（可用剩 1）。買價 30000 ≥ 賣價 29000，成交；成交價採 maker 價 29000，數量 1。

結算後：

- 買方計價幣：凍結 `30000 − 1×29000 = 1000` 仍凍著（多凍部分），可用 70000。
- 買方標的幣：可用 `0 + 1 = 1`。
- 賣方標的幣：凍結 `1 − 1 = 0`，可用 1。
- 賣方計價幣：可用 `0 + 29000 = 29000`。

買方此單此時已完全成交，多凍的 1000 計價幣退回可用 → 可用變 71000、凍結變 0。

### 7. 進階功能

- 多凍結退款（第 5 節）。
- 手續費：成交時對買方收到的標的幣、賣方收到的計價幣各抽一小比例進手續費帳戶。需決定費率與四捨五入方向（永遠對交易所有利，避免湊出免費套利）。
- 帳本流水（見 `02` 6.2）：每次餘額變動寫一筆帳本紀錄，供結算完整對帳。
- 對帳工作：定期掃描所有錢包「可用＋凍結」總和是否守恆，抓出潛在錯誤。

## 二、開發方規格

> 對應 app：`transaction` / `member`　主要 model：`TransactionModel`、`WalletModel`

### 1. 結算函式與原子邊界

實作一個結算函式，輸入一筆成交（買單、賣單、成交數量、成交價），原子地搬動四個錢包餘額。四個錢包改動，加上建立 `TransactionModel`、更新兩張訂單狀態，必須全部包在同一個 `transaction.atomic()` 內。

搬動的四筆餘額對應需求方第 2 節：

- 買方計價幣錢包：`frozen_balance -= 已成交部分應付計價幣`
- 買方標的幣錢包：`available_balance += 已成交標的幣`
- 賣方標的幣錢包：`frozen_balance -= 已成交標的幣`
- 賣方計價幣錢包：`available_balance += 已成交部分收到計價幣`

### 2. 收款錢包自動建立

買方收到標的幣、賣方收到計價幣時，收款方對應幣別的錢包可能尚未存在。結算時需確保收款錢包存在（不存在則自動建立），再進行入帳。

### 3. 相對運算與鎖

- 餘額搬移使用 `F()` 相對運算（如 `F('frozen_balance') - amount`），避免讀後寫的競態。
- 改動前以 `select_for_update()` 鎖住涉及的四個錢包，於同一交易內完成鎖定與更新。

### 4. balance_after 取值

若餘額變動需記錄變動後餘額（`balance_after`），其值必須取自「本次相對運算生效後」的餘額，且每筆變動只計一次，避免重複扣減造成 `balance_after` 與實際餘額不符。

### 5. 不變量驗證

搬動完成後，任一錢包的可用與凍結餘額皆不得為負。凍結扣除的量必須來自「這張單當初凍結」的部分，不可多扣；需配合撮合的待成交量計算。

### 6. 與撮合的串接

結算承接撮合結果：撮合產生一筆成交後立即結算，通常兩者在同一 atomic 交易內完成。

### 7. 技術約束／注意事項

- **凍結不可扣成負數**：結算扣除的凍結量須對應該張單當初凍結的量，配合撮合待成交量計算，不可多扣。
- **四個錢包必須一起鎖、一起改**：只改一半即 commit 會導致餘額對不上，務必置於同一 atomic。
- **手續費四捨五入方向**：捨入方向錯誤可被大量小額單套出免費手續費，捨入須永遠不利於用戶、有利於交易所。
- **退款不可重複退**：同一張買單的多凍結差額只能退一次，退完須標記，避免取消與成交各退一次。
