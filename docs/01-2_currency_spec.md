## 一、需求方規格

### 1. 背景與範圍

範圍二讓系統能真正在測試鏈上收發幣。此時幣別不再只是「有這種幣」的名目，而必須攜帶足以支撐鏈上監聽、入帳、換算與提幣所需的全部業務屬性。

### 2. 幣別身分：代號不足以識別一種幣

同一個幣別代號在不同鏈上是**完全不同、互不相通**的資產。將某條鏈上的幣轉往另一條鏈的地址，資產會永久遺失。

驗收條件：

- 一種幣別的身分必須由「代號 + 所在鏈」共同決定，兩者相同才算同一種幣。
- 系統必須能同時容納「相同代號、不同鏈」的多種幣別，各自擁有獨立的鏈上屬性與收款位置。
- 不得以代號單獨作為幣別的唯一識別。

### 3. 金額精度需求

鏈上金額以該幣種的最小可轉單位計數，不同幣別的最小單位差距可達數十億分之一（例如某些幣別 1 顆等於一億個最小單位，另一些等於 10^18 個最小單位）。

驗收條件：

- 金額精度必須能無損表示到每種幣別的**最小可轉單位**，否則會遺失用戶資產（例如把極小額入金截斷為零）。
- 精度需求橫跨全系統：凡是記錄餘額、訂單、成交、帳務金額之處，都必須達到此精度，且需在系統持有真實資產之前完成調整。

### 4. 每種幣別需具備的業務屬性

- **所在鏈**：這種幣在哪條鏈上。
- **原生幣或代幣**：是該鏈的原生幣，還是由合約發行的代幣。
- **收款合約位置**：代幣型幣別需記錄其合約識別位置；原生幣沒有此項。
- **鏈上精度**：該幣別最小單位與人類可讀單位之間的換算基準，是金額換算的關鍵。
- **入帳確認門檻**：一筆入金需在鏈上達到幾次確認才可入帳。
- **最小提幣量**：低於此量的提幣沒有經濟意義（會被手續費吃光）。
- **提幣手續費**：向用戶轉嫁的鏈上成本。
- **入金開關**：可於該鏈維護或壅塞時暫停入金。
- **出金開關**：可暫停出金。

### 5. 三個獨立閘門

「是否開放交易」（見 `01-1` §6.3）與「是否開放入金」「是否開放出金」是**三個彼此獨立的開關**。系統必須支援各種組合，例如「暫停入金但仍可交易」，或「下架交易但仍允許用戶提幣離開」。

### 6. 確認門檻的安全要求

入帳確認門檻不得設得過低，否則入金可能因鏈重組而被雙花（詳見 `06-2` §2.2）。不同鏈的安全門檻不同，須依各鏈特性設定。

## 二、開發方規格

> 對應 app：`currency`　主要 model：`CurrencyModel`（擴充）

### 1. 唯一鍵調整

- 範圍一將唯一約束設在 `code` 上（`unique=True`）。升級範圍二時**必須移除該單欄唯一約束**，否則無法支援多鏈同名幣。
- 幣別唯一鍵改為 `(code, chain)` 的組合（`unique_together`），使「不同鏈上的同代號幣」成為各自獨立的幣別資料列。
- 替代方案：拆分為「資產（Asset）」與「該資產在某鏈上的發行（Token）」兩層模型，較正規但改動較大；本規格採在 `CurrencyModel` 加 `chain` 欄位的做法。

### 2. 精度 migration（跨全系統）

金額欄位在範圍一為 `DecimalField(max_digits=20, decimal_places=2)`，僅 2 位小數，無法表示鏈上最小單位。升級須執行一次跨錢包、訂單、成交、帳本的全系統 migration，並在持有真實資產前完成。三種可選方案（屆時定案）：

1. **擴大 `decimal_places`**（如 8 或 18），並同步加大 `max_digits`（例如 `max_digits=36, decimal_places=18`），避免整數位不足。
2. **以幣別各自精度驗證顯示**：由 `CurrencyModel.decimals` 決定顯示與驗證精度，DB 統一採一個足夠大的精度儲存。
3. **改以整數儲存最小單位**（如以 `BigInteger` 存 wei / satoshi），顯示時再換算；最不易出錯，但全系統金額運算須改寫。

### 3. `CurrencyModel` 擴充欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `chain` | CharField / choices | 所在鏈（`ETH_SEPOLIA`、`BTC_TESTNET`…）。與 `code` 合起來唯一 |
| `is_native` | Boolean | 原生幣（如 ETH、BTC）或合約發行代幣（如 ERC-20 的 USDT） |
| `contract_address` | CharField(100) | 代幣才有（合約地址）；原生幣留空 |
| `decimals` | PositiveSmallInteger | 鏈上精度，金額換算的關鍵 |
| `min_confirmations` | PositiveSmallInteger | 入金入帳所需確認數 |
| `min_withdraw` | Decimal | 最小提幣量 |
| `withdraw_fee` | Decimal | 提幣手續費（記帳用獨立 reason，見 `06-2` §3.4） |
| `is_deposit_enabled` | Boolean | 是否開放入金 |
| `is_withdraw_enabled` | Boolean | 是否開放出金 |

> `is_active`（是否開放交易）於 `01-1` §6.3 定義，與 `is_deposit_enabled`、`is_withdraw_enabled` 為三個獨立閘門。

### 4. 技術約束/注意事項

- **唯一鍵**：唯一約束須以 `(code, chain)` 為之，不可退回單以 `code` 為唯一鍵。
- **精度**：`decimals` 為每幣別各自的值（不同幣別可為 8、18、6 等），換算時須逐幣別讀取，錯值會造成 10^n 倍的金額偏差。
- **原生幣與代幣分流**：原生幣無 `contract_address`，程式須對原生幣與代幣採兩條處理路徑，不可對原生幣查合約地址。
- **確認門檻**：`min_confirmations` 須依各鏈安全需求設定，過低會有雙花風險（見 `06-2` §2.2）。
